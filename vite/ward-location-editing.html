Ward/Location Editing Feature ​

Overview ​

This feature allows users to edit the ward/location of tests within a 24-hour window after test creation. It also maintains a complete audit trail of all ward movements for a client/patient.

Implementation Details ​

Backend Components (mlab_api) ​

Database ​

  • Table: ward_change_trails - Stores the complete history of ward movements for encounters
    • encounter_id - Reference to the encounter
    • previous_facility_section_id - Previous ward location
    • new_facility_section_id - New ward location
    • changed_by - User ID who made the change
    • changed_by_name - Username who made the change
    • changed_at - Timestamp of the change
    • reason - Optional reason for the ward change
    • Standard voiding fields for audit compliance

Models ​

  • WardChangeTrail (app/models/ward_change_trail.rb) - Model for tracking ward changes

    • Belongs to encounter, previous_facility_section, new_facility_section
    • Validates presence of required fields
    • Serializes ward details with user information

  • Encounter (app/models/encounter.rb) - Updated to track ward changes

    • Has many ward_change_trails
    • Automatically creates trail entry when facility_section_id changes
    • Includes ward_change_trail in JSON response

Controllers ​

  • EncountersController (app/controllers/api/v1/encounters_controller.rb)
    • Sets current user ID before update to track who made the ward change
    • Returns encounter with ward change trail included

Services ​

  • TestService (app/services/tests/test_service.rb)
    • ward_change_trail(encounter_id) - Fetches complete ward movement history
    • Returns trail sorted by most recent changes first
    • Includes ward names, user information, and timestamps

Frontend Components (mlab_core) ​

  • components/tests/view-dialog/index.vue - Main test view dialog with ward editing functionality

Services Modified ​

  • services/endpoints.ts - Added updateWardLocation endpoint

Types Modified ​

  • types/index.d.ts - Added encounter_id field to Test type

Features ​

1. Ward Selection with Search ​

  • Fetches available wards from API endpoint: encounter_type_facility_section_mappings/facility_sections?encounter_type_id=2
  • Displays wards in a searchable dropdown component
  • Shows current ward selection based on test data
  • Real-time search filtering as user types
  • Keyboard navigation support (Enter to select, Escape to close)
  • Click-to-select functionality
  • "No wards found" message when search yields no results

2. Time-based Restrictions ​

  • Ward editing is only allowed within 24 hours of test creation
  • Uses created_date field from test data to calculate time difference
  • Shows lock icon (🔒) when editing is disabled due to time restriction
  • Displays tooltip explaining the 24-hour restriction

2.1 Status-based Restrictions ​

  • Ward editing is not allowed for tests with "verified" status
  • Checks status field from test data to enforce this restriction

3. Ward Change Trail (Audit History) ​

  • Automatic tracking: Every ward change is automatically recorded
  • Complete history: View all past ward movements for a patient
  • User attribution: Tracks who made each ward change
  • Timestamps: Records exact time of each change
  • Available in API: Ward trail is included when querying single test

Trail Data Structure ​

json
{
  "ward_change_trail": [
    {
      "id": 1,
      "encounter_id": 1079732,
      "previous_ward": "ICU Ward",
      "previous_ward_id": 5,
      "new_ward": "General Ward",
      "new_ward_id": 10,
      "changed_by": "john_doe",
      "changed_by_id": 123,
      "changed_at": "2026-04-17T09:30:00.000Z",
      "reason": null
    }
  ]
}

4. Ward Update Functionality ​

  • Updates ward via API endpoint: encounters/{encounter_id}
  • Sends facility_section_id as payload
  • Automatically creates audit trail entry
  • Provides real-time feedback with loading indicators
  • Updates local state immediately upon successful update
  • Shows success/error toast notifications

5. User Interface ​

  • Searchable dropdown with custom styling
  • Disabled state styling for non-editable wards
  • Loading spinner during update operations
  • Visual indicators for edit restrictions
  • Responsive design with proper spacing
  • Hover effects and focus states
  • Dropdown arrow indicator
  • Search input with placeholder text
  • Scrollable ward list for large datasets

API Endpoints ​

Get Available Wards ​

GET encounter_type_facility_section_mappings/facility_sections?encounter_type_id=2

Update Ward Location ​

PUT encounters/{encounter_id}
Body: {
  "encounter" : { facility_section_id: <ward_id> }
}

Response includes:

  • Updated encounter details
  • Complete ward_change_trail array with all historical changes

Get Single Test with Ward Trail ​

GET /api/v1/tests/{test_id}

Response includes:

  • All test details
  • ward_change_trail array showing complete ward movement history
  • Each trail entry includes:
    • Previous and new ward names/IDs
    • User who made the change
    • Timestamp of change
    • Optional reason

Usage ​

  1. Open test view dialog
  2. Available wards are automatically loaded
  3. Current ward is pre-selected based on test data
  4. If within 24-hour window, user can click on ward dropdown to open search
  5. Type in search box to filter wards by name (case-insensitive)
  6. Scrollable list of wards appears below search input and scroll if you cannot see all wards or are just seing the search input
  7. Click on desired ward or press Enter to select first filtered result
  8. Ward is automatically updated when selection changes
  9. Ward change is recorded in audit trail
  10. Press Escape to close dropdown without selecting
  11. Success/error feedback is provided to user
  12. View complete ward movement history in test details

Search Features ​

  • Real-time filtering: Results update as you type
  • Case-insensitive search: Matches regardless of letter case
  • Keyboard shortcuts: Enter to select, Escape to close
  • Visual feedback: Hover effects and clear selection states

Database Migration ​

To enable this feature, run the migration:

bash
cd /path/to/mlab_api
rails db:migrate

This will create the ward_change_trails table with all necessary indices for optimal query performance.

  5. Reporting: Enable ward movement analytics and patient flow reports

Security & Validation ​

  • Server-side validation (assumed)
  • Proper error handling for edge cases
  • Token-based authentication for API calls
